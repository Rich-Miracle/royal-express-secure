FIX - CSRF token not reaching requests
======================================

Replaces pages/head.php and Admin/pages/head.php only.

WHAT WAS WRONG
--------------
The token was published correctly in the meta tag, but the code attaching it to
requests used jQuery's ajaxSetup. pages/assets.php loads jQuery three separate
times: 3.6.0, then 3.4.1 slim, then 3.6.0 again. Each load replaces the global
jQuery object, and any ajaxSetup configuration attached to a previous instance
is discarded with it. So the header was configured and then thrown away before
any request was sent.

THE FIX
-------
The token is now attached by hooking XMLHttpRequest.prototype.open directly.
Every AJAX library on the page, jQuery included, sends through XMLHttpRequest
underneath, so one hook covers all of them regardless of what loads afterwards.
window.fetch is wrapped as well.

TESTING
-------
1. Hard refresh first: Ctrl+F5. The old script will otherwise be cached.

2. As a customer, change your password. The current-password check should now
   pass.

3. Open DevTools, Network tab, trigger the action, click the api.php request
   and look at Request Headers. X-CSRF-Token should be present. Screenshot it.

4. Repeat as admin on a settings change.

5. Check logs\app_error.log. No new csrf_token_invalid entries should appear.

WORTH RECORDING FOR THE REPORT
------------------------------
This is a good example of a control that was present in the code, correct in
principle, and still not working. Only running it revealed the problem, and the
log told you exactly which check was rejecting the request. That is the value of
the security logging added earlier: without it this would have surfaced as
"changing my password says the current one is wrong" with nothing to point at.
